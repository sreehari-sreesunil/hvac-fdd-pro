HVAC-FDD Pro — Architecture & Service Flows

Multi-tenant HVAC fault-detection platform. Six FastAPI microservices, one shared Postgres instance (logically isolated per ADR-0001), MQTT ingestion, and an agentic RAG copilot.

github.com/sreehari-sreesunil/hvac-fdd-pro
System · overview

End-to-end architecture

Frontend and edge devices enter through six independently-deployed services. Every service (except auth-service itself) verifies caller JWTs against one shared secret (ADR-0004) rather than owning its own auth logic. All six write to one Postgres container but six logically separate databases (ADR-0001) — no service ever queries another's database directly.


    

      
Auth boundary: only auth-service issues JWTs. Every other service verifies via common.security.decode_and_verify_token using the same secret (ADR-0004) — a mismatched key silently breaks auth everywhere at once.

      
Data boundary: one Postgres container, six databases (auth_db, asset_db, telemetry_db, ml_service_db, notification_db, copilot_service_db) — cross-service reads only ever go through an HTTP call, never a direct query (ADR-0001).

      
Two data-entry paths: telemetry arrives via HTTP (JSON bulk / CSV) or MQTT (Mosquitto, topic telemetry/{device_id}/readings) — both funnel into the same ingestion function.

      
Closed loop: ml-service's scheduler scores baselines every 60s and raises alerts in notification-service; copilot-service then reads those same alerts as tool-call context when a user asks about an asset.

      
Real multi-tenancy, end to end: organizations, facilities, and asset types are all genuinely org-scoped and RBAC-enforced at the backend (not just hidden in the UI) - verified by walking through the product as a genuinely new user, which is how the asset-type scoping gap (and the platform-wide regression fixing it briefly caused) were actually found.

    

  


  
  

    

      
Service · port 8000

      
auth-service

      
The only service that issues tokens. Owns users, organizations, and invites in auth_db. Every other service depends on it only for JWT verification (shared secret) or, for ml-service's scheduler, a real login as a service account.

    

    

    

      
Endpoints: POST /auth/signup, POST /auth/login, POST /auth/refresh, POST /organizations, GET /organizations, POST /organizations/{id}/invite, GET /organizations/{id}/members.

      
Read/write symmetry, closed a real gap: inviting a member existed long before listing them did - a registered member had no way to ever be seen again. Any real member (any role) can list; only admins can invite.

      
Service-account pattern: ml-service's background scheduler logs in fresh every run as a dedicated least-privilege account rather than caching a long-lived token — simple because the scheduler interval (60s) is well within normal JWT lifetime.

    

  


  
  

    

      
Service · port 8001

      
asset-service

      
Owns the physical hierarchy: facilities → asset types (with their metric definitions) → assets — all genuinely organization-scoped, not just facilities. This is the source of truth every other service resolves a human-readable metric name against.

    

    

    

      
Endpoints: /facilities, /asset-types (carries metric_definitions), /assets — all JWT-protected via the shared-secret pattern.

      
Fan-out: telemetry-service, ml-service, and copilot-service all call this service to resolve a metric name (e.g. RTU_REFG_COND_PRES) to its metric_definition_id for a specific asset.

      
Real multi-tenancy fix: asset types were originally a global, shared catalog across every organization - found live via a walkthrough with a genuinely new org, which could see and use every other org's asset types. Fixed to be organization-scoped, same as facilities, with a real Alembic migration (this service had none before - tables were created via Base.metadata.create_all(), which can't alter an existing table's schema) backfilling existing data and enforcing a per-org uniqueness constraint instead of a global one.

    

  


  
  

    

      
Service · port 8002

      
telemetry-service

      
Three separate doors — HTTP JSON, CSV upload, and MQTT — all converge on one shared _ingest_items() function, so there is exactly one definition of "ingesting a reading" regardless of transport.

    

    

    

      
Never drop data: a reading is written even if its raw external_key (e.g. a BACnet point name) can't yet be resolved to a known MetricDefinition — GET /telemetry/unmapped surfaces what's still unresolved.

      
No cross-DB foreign keys (ADR-0005): metric_definition_id lives in asset-service's database, so telemetry-service can't enforce it as a real FK — resolved at read-time via API instead.

      
MQTT auth: happens at the application layer, not via MQTT's own username/password — each message's ingestion_key is hashed and checked against the same IngestionKey table HTTP ingestion uses.

      
Content-derived idempotency: a caller-supplied idempotency_key is honored as-is; if absent, one is deterministically derived from the reading's own content (asset + metric + value + timestamp, SHA-256). Found live: re-uploading the same CSV twice silently created duplicate rows, since dedup was entirely dependent on a key most callers never supply. Applies consistently across all 4 real ingestion paths (single reading, bulk, CSV, MQTT).

      
Endpoints, closed a real gap: GET /edge-devices now exists - a registered device previously had no way to ever be seen again (only POST existed).

    

  


  
  

    

      
Service · port 8003

      
ml-service

      
Two independent paths through the same core logic: an on-demand API for fitting/scoring a baseline, and a 60-second APScheduler background loop that runs that exact same scoring function for every asset with a fitted baseline and raises alerts automatically.

    

    

    

      
Endpoints: POST/GET /baselines/{asset_id} (fit / score), GET /predictions/{asset_id} and /explain (classifier + gatekeeper models — deliberately not wired into the scheduler yet, per the router's own docstring).

      
Same function, two callers: the scheduler literally imports and calls score_baseline() from routers/baselines.py — the API path and the background path can never silently drift apart.

      
Alert dedup at the source: before creating an alert, the scheduler checks notification-service for an existing OPEN baseline_deviation alert on that asset — one deviation stays one open alert, not one per scheduler tick.

      
Isolated thread: APScheduler's BackgroundScheduler runs jobs on a separate thread from FastAPI's event loop, so a slow scoring run can't block live HTTP requests.

      
Real, caught-same-day regression: when asset-service's asset types became org-scoped, asset_client.py's metric-name resolution wasn't updated to pass organization_id - silently breaking every prediction for every asset on the platform for a full day, undetected by a fully green test suite (this file had 0% real coverage of its own HTTP-calling logic - every test mocked it away). Fixed by adding the real extra hop this needs: asset → facility (for organization_id) → asset-types, plus real tests that actually exercise the HTTP chain instead of mocking it away.

    

  


  
  

    

      
Service · port 8004

      
notification-service

      
A deliberately generic alert sink — it doesn't know or care whether an alert came from the ml-service scheduler or some future source; any producer can POST /alerts.

    

    

    

      
Endpoints: POST /alerts, GET /alerts/{asset_id} (filterable by status), PATCH .../acknowledge, PATCH .../resolve.

      
Consumers: the frontend dashboard for human ack/resolve actions, and copilot-service's get_alert_history tool for conversational context.

    

  


  
  

    

      
Service · port 8005

      
copilot-service

      
A hand-built agentic tool-calling loop (no LangChain) around Groq's LLM API, grounded by a RAG knowledge base (ChromaDB + BGE-small embeddings) and three live data tools scoped to a single, pre-authorized asset.

    

    

    

      
Security boundary: asset_id is fixed at the endpoint level via verify_asset_access — the LLM's tools take metric names/filters only, never an asset_id, so no prompt can trick it into querying an asset the caller doesn't have access to.

      
Embedding asymmetry: documents are embedded raw for storage; queries get an instruction prefix ("Represent this sentence for searching relevant passages: ") before embedding — matching BGE-small's recommended usage.

      
Memory = replay: conversation "memory" is prior turns reloaded under a fixed token budget (oldest dropped first, not summarized) and re-sent with every call — the LLM itself is stateless.

      
Loop cap: up to 5 tool-call iterations per turn before the endpoint fails loudly rather than looping forever.

      
Honest "can't tell" vs. "checked, fine": diagnose_fault used to say "no fault was detected" whenever zero classifiers could evaluate (missing metrics), reading as a false-positive health claim. Found live on a real new asset with minimal data mapped. Now returns models_skipped with real per-model reasons, and the summary genuinely distinguishes "nothing could run" from "ran, found nothing" - reinforced in SYSTEM_PROMPT as a second line of defense.
